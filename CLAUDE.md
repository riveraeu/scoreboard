## Workflow for New Features and Debugging

1. **Check memory and CLAUDE.md** — Read `MEMORY.md` and relevant memory files. Scan CLAUDE.md for the area being changed; load `docs/MODEL.md`, `docs/INFRA.md`, or `docs/FRONTEND.md` if the change touches those areas. For any change driven by calibration data (tuning a formula, adding an input, adjusting a gate), read `docs/MODEL_IMPROVEMENT.md` first.
2. **Plan and get approval** — Present the full plan as text only (files to change, logic, edge cases). **Greenfield vs brownfield check:** for any plan that builds on existing code, briefly ask "what would this look like starting from scratch?" If the from-scratch design diverges from the incremental one, the divergence is either (a) real tech debt worth paying down now, or (b) a load-bearing constraint to keep — name which. This catches bolt-ons that paper over a structural issue (e.g. a chokepoint that already exists, a helper that's redundant because the data's already present). **Core coding-principles check:** before finalizing, run the plan against this repo's load-bearing principles and call out any it violates (with the fix): **(1) Single source of truth** — don't duplicate a value/logic that already lives in one place (`config.js` tunables, `teams.js` registry, a shared helper); edit the source. **(2) DRY / chokepoint** — if the same logic would thread into N call sites, prefer one upstream chokepoint (this session: the shadow funnel vs 10 emit paths). **(3) Least change / YAGNI** — smallest correct change; no speculative abstraction or unused helper (the dropped `features.js`). **(4) Don't break contracts** — additive over destructive; backward-compat for existing keys/columns/routes; never a retroactive formula change (forward-only + `FORMULA_CUTOFFS`). **(5) Failure-closed** — new external/data paths degrade to empty/null, never throw into the hot path (the repo's `try/catch → []` idiom). **(6) Separation of concerns** — keep model / storage / display split (logged-not-modeled features; SimScore display-only). **(7) Match surrounding idiom** — naming, comment density, Web-API style (no Node-only APIs casually). Wait for explicit user approval before editing any files.
3. **Implement** — Make the changes. If backend logic changed, confirm with `/api/tonight?debug=1` (or relevant endpoint) and print key fields proving the change is correct.
4. **Deploy and document** — `git push origin main` to deploy. Update CLAUDE.md (and the relevant `docs/*.md`) in the same commit. Save a memory entry for anything non-obvious future sessions should know.

## What This Is
Sports prop betting dashboard that pulls Kalshi prediction market prices, computes a model True%, and shows qualified plays with edge over the market. Vercel **Node runtime (Fluid Compute)** since 2026-06-11 (was Edge; maxDuration 300 via vercel.json `functions`) — handler code stays Web-API style (fetch/Request/Response/crypto.subtle), so don't introduce Node-only APIs casually.

**Production**: `https://scoreboard-ivory-xi.vercel.app`
**Universal qualification**: Kalshi 67–91% · Edge ≥ 5% (client) / ≥ 3% (server, kept loose for calibration data). Game/team totals gate UNDERs by the same `noKalshiPct ∈ [67, 91]` window. SimScore is display-only since v1 was dropped 2026-05-26. Tunables live in **one source** at `api/lib/config.js` (`KALSHI_GATE` 67, `KALSHI_CAP` 91, `EDGE_GATE_SERVER` 3, `EDGE_GATE_CLIENT` 5); both server (tonight.js) and client (App.jsx, LineupsPage.jsx, TotalsBarChart.jsx) import from there. All client surfaces gate display at EDGE_GATE_CLIENT (5). **Capture vs bet window (2026-06-29 de-blinding):** the `[KALSHI_GATE, KALSHI_CAP]` window gates the `qualified` *bet* flag, but **shadow LOGGING now uses a wider `[CAPTURE_GATE 55, CAPTURE_CAP 97]` favorite-curve band** so calibration sees the full curve (not just the band we bet) and the bet window can be DERIVED from data instead of assumed. Applied at the collection pre-filters in `tonight.js` (game-total/teamTotal/spread "either side" checks + the prop branch) and at the favorite-side selectors in every Phase-1 shadow module (tennis/soccer/soccer-advance/fight/golf-h2h/nascar/mlb-outs — they have no `dropped` fallback, so their window IS their capture gate). This replaced the parked per-category-window idea: the [67,91] cap was capping CAPTURE at the bet ceiling, so `tune:residual` could never see totalBases' edge band above 91¢. `config.test.js` pins `CAPTURE` ⊃ `[KALSHI_GATE, KALSHI_CAP]`. Next: wire the bet window itself to `bettingBoard.discoveredWindow` + Brier eligibility (a per-category constant would just trade one assumption for another) — and in the SAME work demote the fixed **edge gate** (`EDGE_GATE` 3/5) to a per-category data-derived selector subordinate to skill-eligibility. The edge gate is just another hand-set assumption: `edgeBucketRoi` (2026-06-29) shows ROI **flat-negative across every edge band** (no "ROI rises with edge" gradient) — edge is *endogenous* (the model's own claim of mispricing), so it's only real where Brier skill > 0; applied where the market is sharper (every category today) it bets model error. Don't retire it, subordinate it: make skill-eligibility (`bettingBoard.eligible`) the primary live gate (today it only drives board display; the live path still runs `passesCategoryGate` + the fixed edge gate). Untestable inside a sharp category until one exists → forward-only. See [[project-edge-gate-subordinate-to-skill]].

**Model version**: Universal client qualification is `dcQualified === true && edge >= 5 && passesCategoryGate`. `dcQualified` means dc≥7 (only `kalshiStale`/`playerOut` fail; all other dc penalties informational since 2026-06-04). SimScore display-only. Client `EDGE_GATE = 5`; server `EDGE_GATE = 3` (calibration continuity). `trackPlay` stamps `modelVersion: "v2"`; the `qualified` field now carries only alt-line-demotion semantics.

**Category gate (2026-06-01)**: UI display + the `push/notify` cron are restricted to categories with confirmed positive shadow ROI. Gate lives in `passesCategoryGate()` in `api/lib/category-gate.js` (re-exported by `src/lib/constants.js`), applied in `App._qualifiedFilter` / `LineupsPage.passesGate` and the cron. Tracked picks bypass it. **Add a category only when `npm run tune:gate` shows ROI>0 at cumulative n≥50 (`MIN_N_PROMOTE`) AND per-band detail is coherent (no in-window band flipping negative)** — band coherence, not raw n, is the real guard. Current allowed gates: **NONE — the gate is EMPTY as of 2026-06-19.** All four formerly-live categories failed formula-clean validation and were pulled: mlb|strikeouts DEMOTED (in-gate [80,85) n=5/−13%, overconfident 82.5→60, Brier −0.007); wnba|points PAUSED (mis-placed: n=3/−36%, profit at [80,85)/+14% excluded above cap); wnba|rebounds PAUSED (mis-placed/weak: in-gate n=1, real plays ~breakeven, Brier −0.028 @ n=96); wnba|spread PAUSED (overconfident/losing: n=15 hit 20%/ROI −15.5% vs +13.8% claimed edge, Brier −0.032 @ n=237). The gate collapsed under formula-clean scrutiny — consistent with the session-wide Brier finding that nothing beats the market. NOTE: demoting strikeouts is a GATE change, not a formula change; the K_FORM_SIGMA freeze ([[project-strikeouts-formula-freeze]]) still holds and shadow data keeps accruing. Re-enable any category only after tune:gate confirms a coherent +ROI band at n≥50 + non-negative Brier; see memory [[project-live-gate-validation-2026-06-19]]. Plus shadow-only categories (mlb|hits, mlb|totalBases, mlb|outs, tennis|match, soccer|{game,total,teamTotal,spread,btts}, soccer|{1h,2h}{game,total,spread,btts}, soccer|advance, fight|rounds, golf|h2h, nascar|{h2h,top10}, wnba|q{1-4}{total,spread,ml}) and their per-band history → `docs/MODEL.md` § Category gate.

- `api/lib/soccer.js` — **soccer (World Cup) module** (2026-06-21, Phase 1): national-team World Football Elo (`getEloIndex`/`parseEloTsv` from eloratings.net `World.tsv`, 12h KV cache) → `lambdasFromElo` (Elo supremacy split around `SOCCER_MU_TOTAL=2.7` via `SOCCER_ELO_DIV=160`; home_adv=0, neutral WC) → `buildScoreMatrix` (Poisson × Poisson + Dixon–Coles low-score correction `SOCCER_DC_RHO=-0.13`). All 5 market families project off that one matrix: `prob1x2`/`probTotalOver`/`probTeamOver`/`probSpreadCover`/`probBtts`. **Knockout "to advance" (2026-06-25):** `advanceProb(pWin,pDraw,pLoss,k)` folds the 90'-draw mass into a to-advance prob — `P(adv)=pWin+pDraw·w`, `w=0.5+k·(winShare−0.5)`, `winShare=pWin/(pWin+pLoss)`, `k=WC_ADVANCE_ET_SHRINK=0.5` (ET/penalties regression-to-coinflip; provisional, anchored to shootout intuition NOT market). `fetchWcAdvance` reads ESPN `fifa.world` `competitors[].advance` (the ET/pens outcome; falls back to `winner`; exactly-one-flagged guard) for the resolver. `WC_TEAMS` registry (canonical = Kalshi FIFA 3-letter → eloratings 2-letter code + name); `espnToCanonical` (abbr overrides ALG→DZA/HAI→HTI/IRN→IRI + name fallback) + `fetchWcFinals` (ESPN `fifa.world` 90'+stoppage finals for the resolver). **Constants are provisional, anchored to the Elo win-expectancy curve (NOT market prices) — shadow-calibrated.** Phase 2: per-team attack/defence ratings, host bump, club leagues via club Elo. **Shadow-only** (`soccer|*` NOT in category gate).
- `api/lib/mma.js` — **MMA / UFC module** (2026-06-21, Phase 1): the KXUFCROUNDS rounds O/U market only. Pure fight-DURATION model — `WEIGHT_CLASS_FINISH_RATE` (per-fight 3-round finish rate by weight class, provisional, anchored to published UFC finish stats NOT Kalshi) → `roundHazard` (constant per-round finish hazard `h = 1−(1−F₃)^⅓`) → `pEndBeforeRound(h,N) = 1−(1−h)^(N−1)` = P(fight ends before round N). Independent of who wins, so no fighter rating needed (sidesteps thin MMA data). ESPN MMA scoreboard: `getFightCardIndex` (today+8d, 6h KV cache) gives `competition.type.abbreviation`=weight class + `format.regulation.periods`=scheduled rounds for hydration; `matchFightByCodes` ties a Kalshi fighter-code segment (last-name 3+3, e.g. COLTAN) to a bout; `fetchFightResults` reads `status.period`=finish round for the resolver. **Winner market (KXUFCFIGHT) deferred to Phase 1b** (no independent fighter Elo; sportsbook odds would launder the market); **method-of-victory doesn't exist on Kalshi.** **Shadow-only** (`fight|rounds` NOT in category gate). Phase 2: per-round hazard vector + fighter durability, then winner off a fighter Elo.
- `api/lib/golf.js` — **golf (PGA) module** (2026-06-21, Phase 1): the KXPGAH2H single-round head-to-head market only. Field-INDEPENDENT relative-skill model (the golf analog of tennis): `ratingFromPoints` (OWGR average points → strokes-vs-field skill via `GOLF_STROKE_SCALE=1.7`·log10) → `h2hWinProb` (one-round score differential ~ Normal(rB−rA, √2·`GOLF_ROUND_SIGMA=2.8`) with a half-stroke continuity tie band → {pA,pB,pTie}). Rating source = **OWGR API** (`apiweb.owgr.com`, no auth, market-independent; ESPN exposes no golf rating); `buildRatingIndex`/`lookupRating` (full-name → unambiguous last-name, diacritic-tolerant, 12h KV cache, top 600). `fetchRoundScores` reads ESPN PGA scoreboard `linescores[].value` (guarded to [55,100] — drops WD/MC artifacts) for the resolver. **Knobs provisional, anchored to published strokes-gained spreads NOT Kalshi.** **Coverage is thin** — single-round variance keeps most matchups <67%, so few clear the window (accepted; shadow-only). **Shadow-only** (`golf|h2h` NOT in gate). Phase 2: strokes-gained rating + 36-hole field simulation → make-cut + cut-line (the alt-line families).
- `api/lib/nascar.js` — **NASCAR (Cup) module** (2026-06-22, Phase 1): the KXNASCARH2H (driver head-to-head) + KXNASCARTOP10 markets only. Recent-form finishing-position model — μ_d = a driver's mean finishing position over the last `NASCAR_FORM_RACES=10` Cup races (`NASCAR_MIN_RACES=3` to rate), race-to-race spread Normal with `NASCAR_FINISH_SIGMA=9`: `pBeats(μA,μB)=Φ((μB−μA)/√2σ)` (no tie band — positions strictly ordered) and `pTopN(μ,10)=Φ((10.5−μ)/σ)`. Rating source = **ESPN core API** (`sports.core.api.espn.com/.../racing/leagues/nascar-premier`): the `seasons/{Y}/types/2/events` list is the full ~40-race schedule (the league `events` endpoint returns only the active race; event id prefix = YYYYMMDD so race dates need no fetch), each event → `competitions[0].competitors[]` inline `{id (athlete id), order (finish)}`; `buildDriverIndex` aggregates recent finishes + resolves athlete ids→names once (12h KV cache), `lookupDriver` (full-name → unambiguous last-name, diacritic-tolerant). `fetchRaceResults(YYYYMMDD)` returns `{athleteId: order}` for the resolver, matching the Cup event within ±1 day (night races roll the close_time UTC date). **Cup-only by construction** — the index is built from the Cup schedule, so Truck/Xfinity-only drivers drop out at emit (`no_rating`). **Knobs provisional, anchored to finishing-spread intuition NOT Kalshi.** **Shadow-only** (`nascar|h2h`/`nascar|top10` NOT in gate). ## Key Gotchas

**Spread alt-line dedup + category gate interaction (updated 2026-06-05)**: The dedup key is `sp|sport|seg|sortedTeams|line|gameDate`. Different alt lines (e.g. +2.5 vs +3.5) compete independently. Both sides of the same line (MIN +3.5 vs KC -3.5) share one key; the higher-edge side wins. The edge case: if the dedup winner fails the category gate (truePct < 80%) while the demoted loser passes it, `passesGate` (LineupsPage.jsx) and `_qualifiedFilter` (App.jsx) allow the demoted play through — `_altLineDemoted && !passesCategoryGate(p) → false` rather than a blanket block. Opposite-side truePcts are complementary (~sum to 100%), so you can never show both sides simultaneously. Market Report symptom: bold play visible but absent from LineupsPage card.

**TEAM_NORM (Kalshi → ESPN)**: NBA `{ GS→GSW, SA→SAS, NY→NYK, NJ→BKN, NO→NOP, PHO→PHX, WPH→PHX, KAT→ATL }`. WNBA `{ CONNECTICU→CONN, CON→CONN, DALLAS→DAL, WAS→WSH, GSV→GS, LAS→LA }`. After building `STAT_SOFT` rankMaps, a post-normalization loop adds the long-form key so `nbaDefRank["GSW"]` resolves. **Traded volume ≠ resting liquidity (2026-06-15)**: A Kalshi market with `volume_fp:0` (no *trades*) can still have a deep two-sided *resting* book. **Kalshi snap-first read chain (`/api/tonight`)** — 2-tier since 2026-06-22 (`api/lib/tonight/kalshi-pipeline.js`):
1. **`kalshi:snap:{ticker}`** — written every 2 min by cron. All-or-nothing: all fresh (`writtenAt` within 180s) → skip Kalshi REST entirely.
2. **REST + `kalshi:stale:{ticker}`** — per-ticker throttled fetch (3 parallel / 700ms, shuffled) with 30-min stale fallback. Genuinely-fresh, non-empty fetches are **written back to `kalshi:snap:{ticker}`** (chunked via `pipeWriteChunked`, fresh `writtenAt`) so the next request takes Tier 1; stale/rate-limited/failed series are NOT re-stamped (their `kalshi:stale:{ticker}` fallback still serves).

The old **`kalshi:bundle:{date}`** middle tier was **retired 2026-06-22** — it was one un-chunked SET of the whole slate, which silently 413'd (`.catch(()=>{}`) once the slate grew past Upstash's 10MB request cap (soccer/fight/golf/nascar/WNBA-quarters), surfacing only as an Upstash "Max Request Size" email. The 6/12 snapshot-cron chunk-at-7MB fix had missed this parallel write. Both writers now share **`api/lib/kv-pipeline.js`** `pipeWriteChunked` (one chunker, with the `res.ok` check + `console.error`).

`KXMLBGAME` has the same chain. **Diagnosing `usedSnaps:false`:** check `kalshiSnap.meta` in `/api/tonight?debug=1` — `null` meta means no cron completed in the last 10 min, pointing at a cron-side failure rather than a freshness race; non-zero `meta.snapWriteFailed` (2026-06-12) means Upstash rejected pipeline chunks. The pipeline write is size-chunked at 7MB because Upstash caps any HTTP request at 10MB. See `docs/INFRA.md` for the two-phase cron write design.

**Upstash 10MB cap — third offender `byteam:mlb` (2026-06-29)**: the chunker fixes *multi-key* writes, but a SINGLE oversized value still 413s. `byteam:mlb` (~40 maps incl. historical per-team H2H/splits + weather/FIP/barrel + game-time scoreboard) grew past 10MB, so its un-chunked `cache.put` SET was **failing silently** — `makeCache`'s `cmd()` swallowed the rejection (`.catch(() => ({result:null})`), so the key never persisted (`EXISTS=0`/`TTL=-2` right after a fresh build) and the "Max Request Size" email fired on every `/api/tonight` + `/api/dvp`. No user-facing breakage (tonight.js calls `buildMlbByteam()` and uses the in-memory return; it never reads this cache — the only reader is the `/api/dvp` MLB fallback). Fix: **compress at the chokepoint** — `putMlbByteam`/`getMlbByteam` (mlb.js) gzip+base64 the value via `api/lib/kv-compress.js` (`gzipToString`/`gunzipFromString`, Web-API `CompressionStream`, `gz:`-prefixed so a legacy raw value still parses; failure-closed — a compress error just skips the write). gzip gives ~6-10× headroom. Used by the mlb.js write + both `/api/dvp` MLB sites. **Also hardened the swallow:** `cmd()` now logs `[upstash] HTTP <status>` on any non-OK response so a future oversize surfaces instead of hiding. Lesson: when adding a field to a consolidated KV blob, remember single values are NOT chunked — compress or split if it can approach 10MB (NBA `byteam:nba` is the next candidate in-season).

**Neon HTTP SQL API (`api/lib/neon.js`) — four gotchas**:
1. Uses `@neondatabase/serverless` (Edge-compatible). Raw fetch to the Neon hostname fails with "missing authentication credentials" — the Vercel-managed host doesn't accept manual `Authorization: Basic` headers.
2. `neon().query(sql, params)` returns the rows array **directly** (not `{ rows: [...] }`). Do NOT do `result.rows ?? []`.
3. DDL must go through `neonExec()` which splits on `;` and runs each statement separately. Multi-statement DDL in a single `query()` call fails with "cannot insert multiple commands into a prepared statement". `sql.unsafe()` is a raw-value marker, NOT an executor.
4. **DATE columns come back as JS Date objects.** `String(row.date_col).slice(0,10)` gives locale format. Always use `new Date(row.date_col).toISOString().slice(0,10)`.
