## Storage: Upstash Redis
On Vercel, `env.CACHE` (Cloudflare KV binding) is unavailable — `makeCache()` falls through to Upstash REST client (`UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`).

**Free tier 500k commands/month** — when exceeded, all reads/writes silently return null (Upstash returns HTTP 400 but the `cmd()` wrapper only extracts `result`). Diagnose with `curl -H "Authorization: Bearer <ADMIN_KEY>" .../api/auth/debug-redis`.

User auth (`user:{email}`) and picks (`picks:{userId}`) live in the same Redis. JWT expires after 365 days. Picks also kept in `localStorage` as backup — restored to server if server returns 0 but local has data.

## Deployment
- Vercel Node runtime / Fluid Compute (since 2026-06-11; was Edge with a 60s wall — the cause of the 2026-06-10 pregame-snap 504s). `maxDuration: 300` via the `functions` block in vercel.json. `runtimeCtx.waitUntil` is the real `@vercel/functions` waitUntil, so backgrounded work (DvP rebuilds) survives the response. Auto-deploys on `git push origin main` (no `vercel` CLI). Frontend built by Vercel via `npm run build`.
- Rewrites in `vercel.json`: `/api/:path*` → `/api/[...path]`. CORS headers also there (required for OPTIONS preflight through rewrite layer).
- Crons (`vercel.json`):
  - `/api/keepalive` — daily at noon UTC. Keeps Upstash from idle-suspending.
  - `/api/kalshi-series-scan` — `45 12 * * *` (5:45am PT; moved earlier from `15 16`/9:15am on 2026-06-25 so it now runs 15 min BEFORE the `0 13`/6am report — same-day detections land in that morning's `newMarkets` + the "Triage N detected markets" Do-this banner instead of lagging a full day). Bearer-auth via `CRON_SECRET` (or `ADMIN_KEY` for manual). Fetches Kalshi's `series?category=Sports` catalog (~2200 series, single call, no pagination as of 2026-06), diffs it against `SERIES_CONFIG`∪`CRON_ONLY_TICKERS`, and records unknown tickers in Neon `kalshi_series_seen` (`ticker` PK; `status` ∈ new|adopted|dismissed|baseline; `first_seen`/`last_seen`; `tags`/`frequency`/`sample_market`/`sample_subtitle`). **First run baseline-seeds** every currently-listed unknown as `status='baseline'` (silently ack'd) so only series Kalshi lists *after* day-one surface as `status='new'`. A known ticker absent from the catalog (NFL props off-season) is normal — the diff is one-directional. `status='new'` rows render in `/api/shadow-report.newMarkets` and are enriched with one sample market each (capped at 25/run). Reconciles: a `new` ticker later added to `SERIES_CONFIG` auto-flips to `adopted`. Returns `{ok, isFirstRun, catalogCount, knownCount, inserted, newCount, newTickers}`. `?dry=1` skips all writes; `?dismiss=KX..`/`?undismiss=KX..` (admin) move noise out of / back into `new`.
  - `/api/polymarket-scan` — `40 12 * * *` (5:40am PT, just ahead of the Kalshi scan + report). The Polymarket mirror of the series scan. Bearer-auth via `CRON_SECRET` (or `ADMIN_KEY`). Fetches the Gamma league catalog (`GET /sports`, ~300 rows of `{sport: slug, series: id, tags}`), diffs it against `POLY_SERIES` (slug or series id counts as known), and records unknown leagues in Neon `polymarket_sports_seen` (`sport` slug PK; same `status` funnel new|shortlisted|adopted|dismissed|baseline; enrichment cols `sample_event`/`live_event_count`/`market_types` = distinct `sportsMarketType` families in live events — a new market family like total-corners surfaces there, not as a new row). **First run baseline-seeds** all currently-listed leagues; only leagues Gamma adds after day-one surface as `new`. Reconciles against `POLY_SERIES` (→adopted) and `POLY_DISMISSED_SPORTS` in `polymarket.js` (→dismissed). `new`/`shortlisted` rows merge into `/api/shadow-report.newMarkets`/`shortlistedMarkets` with `venue:"polymarket"` + `ticker` = slug, so the ReportPage triage banners and the brief's fresh-detection diff need no frontend change. Returns `{ok, isFirstRun, catalogCount, inserted, newCount, refreshed, newSports}`. `?dry=1` skips writes; `?dismiss=`/`?undismiss=`/`?promote=`/`?unpromote=` (admin) triage by slug.
  - `/api/kalshi-snapshot` — `*/2 * * * *` (every 2 min). Pre-warms `kalshi:snap:{ticker}` so `/api/tonight` skips per-request Kalshi REST. Bearer-auth via `CRON_SECRET` (Vercel auto-attaches when set). Returns `{ok, successCount, failedCount, failed[], durationMs, snapWriteSent, snapWriteFailed, depthWriteFailed, writeErrors[], depthOk, depthFail, depthTargets, depthBudgeted, touchedSeries}`. Series fetched in throttled batches of 3 with 700ms delay; pipelined Upstash write. **Two-phase write (2026-05-31):** snaps written first (so they always land within the ~25s Edge ceiling), then orderbook depth fetched best-effort under a 21s wall-clock deadline and only the touched series re-written. Before the split, the depth phase ran before the only write and timed the cron out on full slates → no snaps at all. **Chunked pipeline write (2026-06-12):** Upstash rejects any HTTP request over 10MB; the single-request pipeline body hit ~11MB after KXMLBTB + the KXMLBHIT ticker fix added ~4.2MB of markets, and the bare `fetch` (no `res.ok` check) swallowed the 413s silently — snaps expired while `_meta` (written in the small phase-2 request) stayed fresh, making the meta diagnostic lie. `_pipeWrite` now chunks commands at 7MB serialized, checks `res.ok` + per-command errors, never throws, and returns `{sent, failed, errors}`. Meta is written in its own tiny request *after* the snap chunks and carries `snapWriteFailed`/`snapWriteError`, so fresh meta once again implies the snap phase ran — check `snapWriteFailed > 0` when diagnosing `usedSnaps:false`. Response `ok` is false if any phase-1 chunk failed.

## Route Contracts

### `/api/tonight`
Main play generation. `?debug=1` returns `dropped[]`, `preDropped[]`, and debug fields. `?bust=1` bypasses all caches. 2-min polling loop in `App.jsx` (`POLL_MS=120_000`), paused when tab hidden. Manual ↻ button is the only `?bust=1` path.

**Edge SWR (2026-06-15):** the normal (non-debug, non-bust) response sets `Cache-Control: public, s-maxage=120, stale-while-revalidate=86400` (header plumbed via the new string-opts branch of `jsonResponse`). Snap-first assembly is ~7s even when snaps are warm, so the Vercel CDN serves a cached copy fresh for 2 min — matching the snap cron + client poll cadence so the displayed set is no staler than the 2-min poll already allowed — then serves the instant stale copy for up to 24h while revalidating in the background. The long SWR window targets the solo-user cold-open case: opening the app after hours idle still returns instantly (a possibly-stale play SET that self-heals on the next 2-min poll) instead of paying the 7s on a fully evicted edge cache. Together this removes the synchronous 7s wait from essentially every load. Safe because display-price staleness no longer carries placement risk: the order modal walks the live book at placement ([[project_orderbook_live_walk]]). `?bust=1` and `?debug=1` stay `no-store` (bust = manual fresh; debug feeds shadow-snapshot logging) so neither serves nor populates the shared CDN cache. **Tunables:** raise `s-maxage` (e.g. 300) for fewer background revalidations at the cost of newly-qualified plays surfacing later; the chosen `stale-while-revalidate=86400` was a deliberate pick over a cron-warmed KV pre-assembly (rejected as redundant with the CDN SWR — the only gap it would close, fresh-on-cold-open, wasn't worth ~700 background assemblies/day).

### `/api/kalshi-order`
`POST`, authenticated (bearer JWT). Body: `{ ticker, side: "yes"|"no", price: int (1–99), count: int }`. Signs via **RSA-PSS / SHA-256 / saltLength=32** with `KALSHI_API_KEY_ID` + `KALSHI_PRIVATE_KEY`. Signature message: `timestamp_ms + "POST" + "/trade-api/v2/portfolio/events/orders"` (ms timestamp, path only, no body). Supports PKCS#1 and PKCS#8 PEM.

**V2 event-order migration (2026-07-17):** Kalshi sunset the legacy `POST /portfolio/orders` (returns "Please switch to the V2 endpoints"). Orders now POST to `external-api.kalshi.com/trade-api/v2/portfolio/events/orders` — a single book quoted in **YES terms**: `side:"bid"` = buy YES, `side:"ask"` = sell YES ≡ **buy NO at the complement** (ask @ `(100−p)/100` costs p¢/contract). Fixed-point dollar-string `price`/`count`, required `client_order_id` (UUID, handler-generated), `time_in_force:"good_till_canceled"`, `self_trade_prevention_type:"taker_at_cross"`. The handler is the translation chokepoint both directions: the client body above is unchanged, and the V2 response (`fill_count`/`remaining_count`/`average_fill_price` — YES-terms dollar strings) is normalized back to the legacy `order` shape — frontend still reads `taker_fill_count`/`taker_fill_cost` (per-contract cost = complement of YES fill price on NO buys), stamps pick with real fill (`kalshiCount`/`kalshiAvgCents`/`kalshiRestingCount`). Reads (markets/orderbook/balance/fills) remain on their legacy `api.elections.kalshi.com` paths — still served; migrate only if Kalshi sunsets them too.

**"Place All" batch (⚡ button in LineupsPage toolbar):** sequential POSTs (await each). Candidate set = qualified minus tracked minus started minus null-sizing. Sizing (`_placeAllSizing` in App.jsx): ⅛-Kelly on bet side (UNDER uses `noTruePct`+`noKalshiPct`), $500 cap / $30 fallback. **Flow A validation:** `validateCandidate(play, sizing)` in `src/lib/placeValidation.js` → `{ hard, soft, risk }`. Three tiers: **hard** = not placeable (✗ greyed, excluded from `placeAllPlaceable`); **soft** = warn but stays checked (⚠ yellow); **risk** = placeable but **auto-UNCHECKED by default** (⚠ orange bold + "tick to override") so thin/untested-market plays aren't bet by accident (2026-06-13). `placeAllPlaceable` (hard.length===0) is the **single source of truth for all four count surfaces** (toolbar badge, tab badges, card badges, modal) — risky plays stay *in* placeable (orderable), they just start unchecked. Hard checks: dcQualified+edge≥5, ticker present, count≥1, price in range, distinct teams. Soft: slippage ≥3¢ over `rawKalshiPct`/`rawNoKalshiPct` (pre-blend top-of-book), wide bid-ask (>8¢), lineup not confirmed (player props). Risk: `kalshiVolume===0` (untested price — a large edge is likely a stale-quote artifact) or `lowVolume`/`thinMarket`. Default selection inits to **safe IDs only** (`risk.length===0`), guarded by `placeAllInitedRef` (reset on close) so an all-risky slate can't loop and "deselect all" stays empty; header shows `N risky (unchecked)`. **Notification gate (2026-06-13):** `useTonight.js` pings only when a play is qualified **and** not risky — it shares `isMarketUntrusted(play)` (exported from `placeValidation.js`: `kalshiVolume===0 || lowVolume || thinMarket`) so the ping matches Place All's default-checked state. A qualified-but-risky play is left UN-seeded in `seenIdsRef` (not pinged, not marked seen), so when its market later develops volume it becomes "fresh" and notifies then — instead of pinging on a stale zero-volume quote we'd never auto-bet. The play still *displays* (guarded/unchecked) the whole time; only the push notification waits. `placeAllPlaceableIds` + `placeAllCountByDay` passed to LineupsPage; 5th param to `playsForGame` filters card display. `activeDayTab` lifted to App.jsx (shared by modal + page). **Modal is today-only** (PT date of gameTime; 2026-06-12) — tomorrow's pre-listings qualify on the page but don't appear in the modal until their slate day. Rows show side-aware True% / Mkt% (price as percent) / Edge%; American odds removed from rows. The toolbar ⚡ badge is also today-only (`placeAllCountByDay[todayPT]`), matching the modal; the button hides entirely when today's count is 0 even if tomorrow pre-listings qualify. **Prop dedup:** highest-edge per `playerId|sport|stat|gameDate`; tracked-pick suppression uses the same day-scoped key and only ACTIVE picks (`!p.result`) — an unscoped key built from full pick history hid every previously-bet player from Place All and the Lineups page for 3 days (6/09–6/12, fixed 2026-06-12). **Phi-scaled sizing:** `placeAllGrouped` groups by game key, `avgPosPhi` from module-level `_SAME_GAME_PHI` Map (App.jsx, φ from shadow analysis), `effectivePlays = 1 + (n-1)×(1-avgPosPhi)`, proportionally rescales counts. Update `_SAME_GAME_PHI` when shadow-analysis reports new strong pairs (n≥50).

### `/api/kalshi-balance`
`GET`, authenticated. Returns `{ cashCents, positionsCents, balanceCents, balanceDollars }`. `balanceDollars` = cash + open-position cost basis (sum of `market_exposure_dollars` over unsettled positions). Two signed RSA-PSS GETs: `/trade-api/v2/portfolio/balance` then positions endpoint. Positions call degrades to `positionsCents=0` on failure. Cost basis, not mark-to-market. No caching.

### `/api/kalshi-snapshot`
Cron-only (`*/2 * * * *`). **Two-phase write:** (1) fetch all series → write snaps immediately with `_meta.depthPending:true`; (2) fetch orderbook depth for in-window markets best-effort under 21s wall-clock deadline (`DEPTH_DEADLINE_MS`, cap `DEPTH_FETCH_CAP=90`, volume-prioritized) → re-write only touched series. Snaps always land regardless of the depth phase. `_meta` carries `depthOk`/`depthFail`/`depthTargets`/`durationMs`. Ticker list derived from `[...Object.keys(SERIES_CONFIG), ...CRON_ONLY_TICKERS]` in `api/lib/series-config.js`.

### `/api/auth/calibration`
Returns `overall`, `byCategory`, `byCategoryDetail`, `kStrikeouts` — tracked pick outcome stats.

### `/api/auth/shadow-calibration`
`GET`, bearer JWT or `?adminKey=`. Queries Neon `shadow_plays`. Optional filters: `?since=YYYY-MM-DD` (default 30d), `?bestThreshold=true` (dedup to one play per group), `?dcQualified=true`, `?minDc=N`, `?sport=mlb`, `?thresholdRank=1`, `?seasonType=2|3`. Returns `overall`, `byCategory` (with `nRaw`/`avgGroupSize`), `byCategoryDetail` plus `roi` and `avgEdge` per cell. Bands 55–60 through 95+ (bet-side probability — UNDERs flip to `1 − model_true_pct`).

### `/api/auth/shadow-analysis`
`GET`, bearer JWT or `Authorization: Bearer $ADMIN_KEY`. Five analyses on `shadow_plays` (since=30d default): (1) `thresholdRankRoi`; (2) `intraGroupCorr` — alt-line group unanimity; (3) `sameGamePairs` — pairwise φ (threshold_rank=1, n≥10); (4) `concentration`; (5) `clvAnalysis` — per-category CLV, edge at snap vs close, hit rate. Requires `price_pre_at IS NOT NULL` rows.

### `/api/auth/shadow-stats`
`GET`, admin bearer. Row counts by date/category/dc + `unresolvedByCategory`. `?trigger=1` also runs shadow-snapshot inline; `?resolvetrigger=1` runs shadow-resolver.

### `/api/auth/clear-kalshi-stale`
`POST ?ticker=KXMLBTEAMTOTAL` with `Authorization: Bearer <ADMIN_KEY>`. Deletes `kalshi:stale:{ticker}`. Does **not** affect `kalshi:snap:{ticker}`.

### `/api/shadow-snapshot`
Cron-only (`5 15`, `10 15`, `5 22`, `35 22 * * *` UTC). Reads `shadow:staging:{date}` from KV first (written by the tonight handler on every recompute, TTL 6h, payload `{plays, dropped, schedule, writtenAt}`); falls back to fetching `/api/tonight?debug=1` (55s timeout). **Coverage check:** `schedule` carries today's ESPN game count per sport (stamped by tonight from gameScores); snapshot compares distinct games in the logged rows (`sport|sortedPair`, **only rows with `game_date === snapshotDate`** — null-date rows are next-day pre-listings or dateless module rows, not capture evidence) against it and returns `coverage: {sport: {games, scheduled}}` + `coverageWarning: true` below 80% (warn-only — catches whole-game gaps from parse bugs/Kalshi outages/emit regressions; legitimate <100% from games without Kalshi markets and DH collapse). `coverage: null` on the HTTP-fallback path. **Persisted** to KV `shadow:coverage:{snapshotDate}` (`{coverage, coverageWarning, at}`, TTL 3d) via **max-merge** (`mergeCoverage`, exported for tests): per-sport `games`/`scheduled` take the max of the existing stamp and this run over the union of sports, warning recomputed from the merged numbers. Coverage within a day is monotonic (same doctrine as the report's resolution KV floor), so a late/manual snapshot run over decayed evening staging — day games settled out of Kalshi, tomorrow's pre-listings staged — can only add coverage, never erase the healthy cron stamp (the 2026-07-06 false "slate under-logged" banner). The next morning's `/api/shadow-report` data-health header reads this KV (the report can't recompute coverage without an ESPN slate fetch). Combines `plays + dropped`, annotates `group_id`/`threshold_rank` (rank 1 = closest to 50% truePct; team rows key **stat-first** — `p.stat || p.gameType`, matching the analyses' `COALESCE(stat, game_type)`; the earlier gameType-first key merged ml/f3ml/f5ml/f7ml into one rank group and starved every segment category's rank-1 population — fixed 2026-07-13 and ALL historical team rows re-ranked the same day, so stored ranks are uniformly stat-first), batch-upserts to Neon `shadow_plays`. **`?rerankgroups=1` (ADMIN only, `&dry=1` to report without writing)**: one-shot maintenance action that recomputes `group_id`/`threshold_rank`/`group_size`/`is_best_edge` for all team rows under the current key — safe to backfill because ranks are pure annotation over stored values (no superseded-formula mixing); idempotent (re-run dry shows 0 changed). Regen the report (`/api/shadow-report?bust=1`) after applying. Stores `home_team`/`away_team` as `homeTeam || playerTeam || gameTeam1`. **Full Kalshi price range:** `dropped` includes game/team total OVERs and ML/spread outside [67,91] (`reason: "kalshi_out_of_window"`). Decimal price columns: `kalshi_yes_price = kalshiPct/100`, `kalshi_no_price = noKalshiPct/100`.

### Shadow maker engine (`api/lib/maker.js`, 2026-07-19)
Simulated maker quoting — V1 is measurement only, NO real orders. Thesis (pooled market-calibration scan 7/19, n=44.5k): the venue's vig sits on the favorite ask (2–8¢ above realized frequency at 80–97¢) while longshot asks are ~fair, and maker fees are ZERO on every configured series except the four major `*GAME` series (`MAKER_FEE_SERIES`). Three phases:
- **Quote** — runs at the tail of the `/api/kalshi-snapshot` cron (books already in hand, zero extra Kalshi calls; skips with `{skipped:"no_staging"}` before the day's first tonight run). Eligibility per market (`computeMakerQuote`): fee-free series, all four book quotes present, unified spread ≤ `CAPTURE_MAX_SPREAD`, neither ask ≥98 (stale regime), known future `gameTime` (pre-game only), favorite ask ∈ `MAKER_BAND` [80,97]. Quote = sell that side at ask − `MAKER_INSIDE_C` (1¢), size `MAKER_SIZE` (10). Segments in Neon `maker_quotes` (open row per ticker; price/eligibility change closes `valid_to` + opens a new row). Each segment stamps `shadow_row_id` (`shadowId` from `api/lib/shadow-id.js`) for settlement.
- **Fill** — nightly in `/api/shadow-resolver` after batch resolve (`detectAndGradeMakerFills`, failure-closed): replays the public trade tape (one `markets/trades` page per quoted ticker, `min_ts` = day start −6h; first 429 aborts the remainder) — a taker trade on our sold side at price ≥ our ask inside a segment window is a simulated fill (we quote strictly inside the book, so price priority is ours); contracts cap at `MAKER_SIZE` per segment. Idempotent via `UNIQUE(quote_id, trade_id)` in `maker_fills`.
- **Grade** — same pass: joins ungraded fills → `maker_quotes.shadow_row_id` → resolved `shadow_plays`; `side_won` derives yes-outcome from the row's bet-side `won` + `direction`, `pnl_cents = fill_ask − 100·side_won`.
Report: `makerBoard` in `/api/shadow-report` (quote volume, fill economics incl. `pnlLoCI_fillLevel_SUPERSEDED`, and the adverse-selection check — sold-side win rate on FILLED quotes vs latest-quote outcomes on ALL quoted markets). `/model` renders it as the SHADOW MAKER card. **Arm criterion for V2 (real resting orders): fill PnL CI-lo > 0 at n≥200 fills** — forward-only, human-applied. ⚠ **Superseded 2026-07-26 — that criterion alone is NOT sufficient; see § Day-clustered CI below.** The gate is now `armCriterion.met` = n≥200 fills AND ≥14 days AND `dayClustered.loCI > 0`. Known measurement biases: 2-min quote lag makes shadow PnL conservative (stale quotes get hit on adverse moves); queue priority is ours by construction; self-effect on taker behavior is the one unmeasured optimism.

**ARM review 2026-07-21 — criterion met in aggregate, but band-scoped.** At 701 graded fills the aggregate cleared the bar (avg +4.35¢, CI-lo +1.54¢), but the per-band ladder (`makerBoard.bands`) shows the edge lives entirely in `80–84` (n=295, avg +11.17¢, sold-side-won 70.2% — CI-lo well above zero on its own). `85–89` (n=227, avg −0.26¢, won 87.2%) and `90–96` (n=179, avg −1.04¢, won 92.7%) are statistically indistinguishable from zero; pooling them into the full `[80,97]` band is what makes the aggregate look better than any sub-band earns on its own (Simpson's-paradox shape). **Decision: if/when V2 (real orders) is built, scope `MAKER_BAND` to `[80,84]` only — do not arm the full `[80,97]` range.** `85–97` stays shadow-only (V1) to keep accruing n; re-score that slice's CI once it separately clears n≥200. V2 order-placement code does not exist yet — this is a scope decision recorded ahead of that build, not a flag flip.

**Floor dropped 80→55 same day (measurement-only)**: the pooled market-calibration scan (`project_pooled_market_calibration`) already showed ask-richness at 70–75 (−1.9¢) and 75–80 (−2.5¢) comparable to or exceeding the 80–85 slice that turned out to be the one real edge — so the edge boundary was never validated to sit at 80, that was just where V1 happened to start quoting. `≤35¢` longshot asks are separately established as ~fair (no vig), so that end isn't worth re-testing. `MAKER_BAND[0]` dropped to 55 to cover the unstudied 55–79 gap; the report's band ladder (`handlers/shadow.js` maker-board query) was widened to 5¢ buckets (`55-59` … `75-79`) alongside the existing `80-84`/`85-89`/`90-96`. Still shadow-only — zero capital risk — this only feeds more data into the V2-scope decision, doesn't change it.

### Maker tape backfill (`api/lib/maker-backfill.js`, 2026-07-28) — replaying days instead of waiting for them
**The arm gate's binding constraint is DAYS, not fills.** At the 7/28 reading V1 had 14,974 fills but only 9 days: `weighted` +1.55¢ CI [+0.70, +2.41] (looks armed) vs `dayClustered` +1.55¢ **se 2.18, CI [−2.71, +5.82]**. Clearing `loCI > 0` needs se ≤ 1.55/1.96 = 0.79, and se falls as 1/√m, so m ≈ 9·(2.18/0.79)² ≈ **69 days** — ~60 more calendar days, and only if a noise-driven point estimate happens to hold. Days needed scales as **(sd/mean)²**, so more fills per day buys nothing.

Kalshi serves enough history to replay those days now (all verified live 7/28):
- `GET /series/{s}/markets/{t}/candlesticks?period_interval=1` → `yes_bid`/`yes_ask` OHLC per minute, retained ≥8 weeks (checked on a 6/02 market).
- `GET /markets/trades?ticker&min_ts&max_ts&cursor` → the same public tape the live path replays.
- `GET /markets?series_ticker&min_close_ts&max_close_ts` → the day's market universe.

The engine spec has been frozen since 7/19, so replaying it over earlier days is **out-of-sample in time**, not a refit.

**Reuse is the whole design.** Eligibility (`computeMakerQuote`) and fill detection (`replayFills`) are imported from `maker.js` untouched. The module adds only `buildSamples` (sparse candles → 2-min poll-cadence series, carrying the last close across gaps) and `segmentsFromSamples` (series → segments). Reimplementing either would make the live-vs-backfill comparison measure the drift instead of the data.

**The NO side** comes from `no_bid = 100 − yes_ask`, `no_ask = 100 − yes_bid` — verified exactly across live books. This is NOT the synthesis CLAUDE.md warns against: that warning is against `100 − yes_ASK`, which lands on the bid side and understates the NO ask by the whole spread. Taking the NO ask off the YES BID is the identity `computeMakerQuote` already assumes when it derives one shared `spread`.

**Scope: the five MLB prop series** (`KXMLBKS/HRR/HIT/TB/OUTS`). They encode `HHMM` in the event ticker, so `kalshiTickerGameTime()` (new in `kalshi-ticker.js`, DST-correct via `Intl` offset resolution) supplies the pre-game gate's `gameTime` with no `shadow_plays` join — which matters because `kalshi_ticker` only exists from 7/23, so a shadow-joined backfill would reach back zero useful days. Date-only series (WNBA props, tennis, UFC, NBASL) and dateless ones (golf, NASCAR) are out of scope rather than guessed at. None carries maker fees.

**Endpoint**: `/api/shadow-snapshot?makerBackfill=YYYY-MM-DD` (ADMIN_KEY). 2,610 MLB prop markets closed on 7/27, more than one 300s invocation walks, so it is `&offset=`-resumable via `nextOffset` (ticker list cached in KV 6h for a stable slice). `&validate=1` replays an overlap day restricted to tickers the live cron also quoted and returns the live-vs-replay comparison; `&compare=1` re-reads it; `&purge=1` drops the validate rows. Idempotent per chunk (delete-then-insert on the chunk's tickers), so partial, repeated, and out-of-order runs all converge.

**One day is either live or replayed, never both** — `maker_quotes.source` (`'live'` default, so every pre-existing row is correctly labelled without a migration) and the endpoint 409s on a day that already holds live segments. `detectAndGradeMakerFills` filters to `source='live'` so the nightly pass never re-walks backfilled segments; `gradeMakerFills` is source-agnostic and grades both.

**Validation is the gate on the whole approach** — a replayed 7/24 must reproduce the live day's PnL before any backfilled day is read. `compareSourcesForDay` returns segments/tickers/avgAsk/fills/contracts/pnlPerContract per source plus `bookNoAskMismatches`, the direct check on the complement identity against stored live values (must be 0). The one assumption it exists to test: candle gaps are carried forward as "unchanged". That cannot invent a fill (a trade IS activity and would emit its own candle, so a gap is provably trade-free) but it does affect segment duration.

**Off-by-one caught by replaying real data, worth remembering**: the final open segment closes at last-sample + one poll interval, and the 2-min grid rarely lands on first pitch — unclamped it ran to 23:46 on a 23:45 game, and a trade in that overshoot is an *in-play* trade producing a fill V1 never makes. Now clamped to game time. Pinned by a test using an odd-minute grid offset, since an even one hides it.

Known deliberate difference: the live tape read is one 1000-trade page per ticker, the backfill paginates. A pre-game prop window carries single-digit trades in practice (6 on the market this was verified against), so they agree everywhere it matters; the validation quantifies the gap rather than assuming it away.

dissolutions, all on the same ~9 days:

**What HAS replicated every time: the vig on the QUOTE** — +1.64¢ over 108k segments, +1.53¢ on the
7/26 rebuild, and the original pooled calibration at n=44.5k. The vig is real. It has never been
shown to survive to a *fill*. The cleanest summary remains the 7/25 one-liner: at a 71.9¢ average
fill the sold side won 71.86% — efficient to 0.04pp — reproduced independently by the replay at
74.3% on a 74.3¢ ask.

**`pnlLoCI` renamed `pnlLoCI_fillLevel_SUPERSEDED` (2026-07-28).** The fill-level CI reads like a
headline number and had produced a false green four times — most recently on the landing page's
arm tile, on the morning V2 was shelved, at t=3.56. Renaming it at all seven emit sites means a
new consumer cannot pick it up from autocomplete or a grep for `pnlLoCI` and mistake it for the
gate. The gate is `armCriterion.met`, which reads `dayClustered.loCI`. The one legitimate
remaining consumer (the adverse-selection banner) uses it only to detect an entirely NEGATIVE
interval, where a too-narrow CI over-warns — the safe direction.

**Enforced in code, not config.** `SHELVED = true` in `maker-live.js` short-circuits `isArmed()`
ahead of both existing gates, and `/api/maker-v2-arm` 409s with the reason. This is deliberate:
`MAKER_V2_ARMED` was still `"true"` in production from the 7/21 arming, so shelving would otherwise
have rested on a single KV flag that one POST would flip back. Un-shelving is a one-line code
change with the verdict in front of whoever makes it. The env+KV mechanism is left intact so that
revert stays one line, and `maker-live.test.js` pins the shelved state as a tripwire.

**Not deleted.** `maker-live.js` and `kalshi-order-client.js` stay — the latter is shared with the
manual `/api/kalshi-order` path, so removing V2 would be a much larger change than shelving
warrants.

| half | state | why |
|---|---|---|
| V1 **quoting** (snapshot cron) | **ON** | Free — the cron already holds the books. The quote-side vig is the one finding that has replicated every time, so `maker_quotes` stays a live measurement of the one real effect. `quotedOutcomes`/`adverseSelection` read segments + settlements, not fills. |

### Shadow maker V2 (`api/lib/maker-live.js`, 2026-07-21) — REAL resting orders, `armed=false` by default
Built same day as the ARM review above, scoped tight to `MAKER_V2_BAND` `[80,84]` (config.js) — the one sub-band with a real, non-borderline edge; `[85,97]` stays V1-shadow-only. Places actual limit orders on the account's existing funded Kalshi credentials (`KALSHI_API_KEY_ID`/`KALSHI_PRIVATE_KEY` — the same ones manual Place-All/single-order placement already use), via a new shared client, **`api/lib/kalshi-order-client.js`** (`placeKalshiOrder`/`cancelKalshiOrder`/`fetchKalshiFills`), extracted from the `/api/kalshi-order` handler so the manual and automated paths never drift on the V2 payload/signing (zero behavior change to the manual route — same `_importKalshiKey`/PKCS1→8 logic, now shared).

**Fail-closed kill switch — two independent gates, both required**: `env.MAKER_V2_ARMED === "true"` AND a KV flag (`maker:v2:armed`) — either false stops everything (`isArmed()`/`setArmed()` in maker-live.js). `POST /api/maker-v2-arm` (ADMIN_KEY) sets the KV half only — the env var still gates it, so a KV-only arm is inert until the env var is also set (deliberate: arming for real needs both a deploy-level and a runtime-level action). `POST /api/maker-v2-kill` (ADMIN_KEY) disarms AND cancels every currently resting order immediately, regardless of the env var.

**Order lifecycle avoids per-tick churn**: each resting order is placed with `time_in_force:"good_till_canceled"` + `expiration_time` (`MAKER_V2_EXPIRATION_SEC`=150s past placement) — Kalshi auto-cancels it with no further call if untouched. Each `kalshi-snapshot` cron tick (runs right after V1's `updateMakerQuotes`, same books/staging, zero extra reads) **first polls real fills** (`fetchKalshiFills`, 15min lookback) so anything that filled between ticks flips `resting→executed` immediately — matched rows are excluded from the same tick's cap bookkeeping so they don't double-count against `MAKER_V2_MAX_CONCURRENT`. For anything still resting after the fills poll: unchanged price + not nearing expiry → no-op; nearing expiry (same price) → place a fresh replacement, let the old one lapse on its own; price changed → explicit `cancelKalshiOrder` first, THEN place the new one (never both resting at once — avoids doubled exposure); no longer eligible → no cancel call (Kalshi's `expiration_time` already handles that side), but once past `expires_at` the row is force-flipped to `expired` locally same-tick; newly eligible → place new, subject to `MAKER_V2_MAX_CONCURRENT` (20) and `MAKER_V2_SAME_GAME_CAP` (2, mirrors Place All's `SAME_GAME_CAP` — keyed by `gameKeyFor`, sport+date+sorted-team-pair so ticker home/away order can't split one game into two buckets). `MAKER_V2_SIZE`=5 contracts/order on debut — human-scaled up later, no auto-scaling.

**STATUS-staleness fix (2026-07-22)**: before this, `maker-v2-board`'s STATUS column could show `RESTING` for hours after an order actually filled OR lapsed with zero fill, because the ONLY code that ever polled real fills or force-expired an abandoned resting row was the nightly `reconcileLiveMakerFills` (2am/3:05am/5:50am PT). **Open positions view (`GET /api/maker-v2-board`, 2026-07-22)**: `positions` = the `orders` rows filtered to `status='executed' AND graded_at IS NULL` (currently-held, ungraded — same subset `reconcileLiveMakerFills` grades once resolved), each enriched with a live top-of-book read (`fetchKalshiOrderbook` from `kalshi-book.js`, `pLimit(8)`-bounded, one call per distinct ticker — no full book walk, this is a display estimate not an execution price). Framed as a **short**, matching what V2 actually does (`sellAsBuy` — the real order is a buy of the complement side): `collected` = `price` (premium taken at sale), `currentAskCents` = live ask on the SAME sold side (what it'd cost to close now), `unrealizedCents = price − currentAskCents` (positive = favorite got cheaper = winning), `maxRiskCents = 100 − price`. Failure-closed per row — a failed book fetch just omits the live fields, cost basis still renders. Read-only (no cash-out/buy-more actions wired — Kalshi has no sell-to-close endpoint; a real "cash out" would need the same buy-the-complement trick `sellAsBuy` uses, deliberately out of scope for this display-only pass). Rendered by `MakerLivePositions` in `MakerBoardPage.jsx` — this is now the ONLY orders/positions table on the page (the older raw `MakerLiveOrders` monitoring table, which listed every status including resting/canceled/expired, was removed same day in favor of this positions-only view; per-status counts are still visible via `LiveFillRateTile`'s "N executed / N placed · N resting" line, so nothing needs the old table to know what's resting).

### Adverse selection, measured within band (2026-07-26)

`makerBoard.adverseSelection` + `quotedOutcomes.byBand`. **The old diagnostic was confounded and could invert.** `quotedOutcomes` used `DISTINCT ON (ticker, game_date) … ORDER BY valid_from DESC` — one row per ticker-day, the FINAL quote — so the "quoted" population had avgAsk **75.3¢ vs 73.2¢ across all segments**, while fills come from any of ~10 segments/ticker-day (avgFillAsk 71.0¢). It then compared raw sold-side win *rates* across those mismatched price distributions, and a lower win rate is exactly what a lower price should produce. Symptom: on 2026-07-26 filled edge (+1.42¢) came out ABOVE quoted (+0.57¢) — mechanically backwards for a resting maker, i.e. the metric was measuring mix. (It had also been running through the 414-broken settlement fetch: 2,241 → 7,765 resolved tickers after that fix.)

Now: population is **every segment**, grouped `(band, ticker, quote_side)` and segment-weighted; compared **within band** (band `avgPnl` IS the filled seller edge, `AVG(ask − 100·won)`); headline `gapCents` = quoted edge − filled edge re-weighted onto the quoted price distribution. Sanity check that the population is now representative: `quotedOutcomes.avgAsk` 73.3¢ vs `quotes.avgAsk` 73.2¢.

```
quoted +1.53c | filled raw +1.38c | filled mix-adjusted +1.01c | gap +0.51c
55-59 -1.29  60-64 -2.25  65-69 +1.09  70-74 -2.62
75-79 +8.61  80-84 -1.87  85-89 +0.04  90-96 +2.66      (gap = quoted − filled)
```

**The split is 4 negative / 4 positive** — in 4 of 8 bands fills do *better* than quotes — and the positive aggregate is almost entirely the 75-79 band. Same band-incoherence that retired the 7/21 "edge only in 80-84" claim. **So adverse selection is not currently demonstrated at the ~1.4¢ once believed** — it remains the right prior for a resting maker, but this book doesn't show it, and "more data won't fix V1 because fills select against the quote edge" should not be repeated as established. The DO-NOT-ARM verdict rests on the day-clustered CI below, not on this. The quote-side vig itself does hold up (+1.53¢ over 81.8k segments, consistent with § pooled market calibration).

⚠ `quotedOutcomes.n` is now **segments**, not ticker-days — use `.tickers` for a market count. Band `CASE` lives in one `_makerBandCase()` helper; both sides must bucket identically or the comparison is void again. Banner tier 1.6 + the MakerProgress tile read `gapCents` (fire at ≥2¢), replacing the old ≥8pp win-rate trigger.

### Day-clustered CI — the honest interval (2026-07-26)

`makerBoard.fills.dayClustered` and `makerBoard.live.dayClustered` (`dayClusteredPnl`, `api/lib/maker-stats.js`). Same contract-weighted ratio estimator as `weighted`, but with the **DAY as the cluster** instead of the fill:

```
R = Σ_d Y_d / Σ_d C_d          Var(R) ≈ (m/(m−1)) · Σ_d [Y_d − R·C_d]² / (Σ_d C_d)²
```

**Why**: `weighted` fixed correlation *within* a fill (all contracts share one outcome). This fixes the level above — correlation *across fills sharing a day*. V1 sells favorites, so a day's PnL is essentially one bet on whether favorites underperformed that slate; hundreds of fills resolve off a few dozen correlated games plus one common factor. Treating them as independent is the same error class as the contract-as-observation trap, one level out.

**It is not a small correction.** On V1's book at 2026-07-26 over identical data:

| | mean | se | 95% CI |
|---|---|---|---|
| `weighted` (fill-clustered) | +1.76¢ | 0.54 | **[+0.70, +2.81]** ← the superseded fill-level gate was satisfied |
| `dayClustered` | +1.73¢ | 2.42 | **[−3.00, +6.47]** |

The point estimate barely moves; the interval widens ~4.5× and crosses zero. Cause: +$1,865 of the +$1,066 total came from **two days** (7/24 +$1,005, 7/25 +$860) against −$800 across the other five. Seven days is the real sample size, not 9,415 fills. Both those days are post-dating the 7/24 settlement re-grade, which was a whole-book live mutation, so this is *not* a mixed-basis artifact — the daily figures for 7/19–7/24 are byte-identical before and after.

**`armCriterion` now carries both**: `need` (the original fill-level bar, kept for continuity) and `needClustered` (`dayClustered.loCI > 0`) plus `minDays: 14`, with a computed `met` combining all three. `minDays` is a sanity floor so the interval is estimable at all — necessary, not sufficient. Note the daily SQL gained `contracts_graded` (graded-only contract sum) because pairing the existing all-fills `contracts` with a graded-only `pnl_total` would bias the denominator.

**"Outcome known" ≠ "Kalshi settled" (2026-07-22, later superseded — see below)**: shipping the fast path above immediately surfaced a real gap it hadn't previously been possible to see (the nightly-only path always ran hours after Kalshi had *definitely* already settled everything, masking this). A game ending doesn't mean Kalshi has finished crediting that market yet — row-by-row audit against real final scores confirmed every grade was *correct*, but ~$52 of one day's total came from two WNBA games whose real Kalshi positions were still open/unsettled hours after the final whistle, while our system had already counted them as realized. Worked, but same-day it became clear there was a strictly better source (next entry) — this endpoint is kept around only for the one-off `/api/maker-v2-revert-unsettled` diagnostic (below), no longer in the main grading path.

**Grading rewritten to use Kalshi's own settlements feed (2026-07-22)**: `GET /trade-api/v2/portfolio/settlements` returns, per settled market, `market_result`, `revenue` (GROSS payout, 0 or 100¢/contract — **not** net of cost or fees, corrected after an initial deploy assumed it was already net and overstated every win by its own cost basis), `yes_total_cost`/`no_total_cost`, and `fee_cost`. A ticker only appears here once Kalshi has actually settled it, so this one feed is both the accuracy signal and the timing signal, superseding the earlier `fetchUnsettledTickers` gate. `gradeResolvedMakerPositions` (`maker-live.js`): queries all `status='executed' AND graded_at IS NULL` rows, calls `fetchKalshiSettlements` (`kalshi-order-client.js`, 4-day lookback via `min_ts`), and for any ticker found, grades every matching row as `pnl_cents = grossPayoutPerContract − (100−price) − feePerContract` (our real position is a long in the complement side per `sellAsBuy`, so `100−price` is our own cost basis; fee split evenly across the ticker's contracts same as gross payout). `side_won = market_result === row.side`.

**Full re-grade after finding the OLD formula also had a real sign bug (2026-07-22)**: cross-checking EVERY already-graded row that day against Kalshi's raw settlements (independent of our own DB — `/api/maker-v2-settlements-raw` diagnostic) found the OLD ESPN-derived `side_won` CASE-WHEN formula (unchanged since V2 launched, not something touched in this rewrite) disagreed with Kalshi's real settlement on several spread/team-total markets — genuine sign flips worth tens of dollars each, not rounding noise (e.g. a WNBA spread graded as +$32.80 was really **−$7.61**). The formula had passed an earlier audit that checked the underlying game score/margin was correct, but never independently verified the sign translating that margin into "did our specific sold side win." Fix: `POST /api/maker-v2-revert-all-graded` (ADMIN_KEY) clears `graded_at`/`side_won`/`pnl_cents` for every currently-graded row, letting the settlements-based path re-grade the entire ledger against Kalshi's ground truth — a one-time, explicitly-triggered correction (not automatic), given it touches the whole real-money PnL history. `resolveOpenMakerPositions`'s ESPN-based `shadow_plays` resolution still runs (feeds the broader calibration pipeline), but V2's own PnL no longer depends on it or trusts its derived sign at all.

**Simplified same day: cost/contracts also come straight from Kalshi, not our own rows (2026-07-22)**: the mass re-grade above still used `100−our stored price` as cost basis and our own `filled_count` sum as the contract denominator — both reconstructed from OUR tracking, which is exactly the class of thing that was just proven unreliable. Kalshi's settlement record already reports `yes_total_cost`/`no_total_cost` (whichever side we actually held) and `yes_count`/`no_count` directly, so `gradeResolvedMakerPositions` now computes `netPerContract = (revenue − cost − fee) / kalshiContracts` using ONLY Kalshi's own numbers — zero dependency on our stored `price` or `filled_count` matching reality. `side_won` is kept only as an informational label (`market_result === row.side`); it no longer feeds the PnL number at all.

**V1 (paper) validated against the same settlements feed (2026-07-22)**: `maker.js`'s `detectAndGradeMakerFills` grades `maker_fills` with the identical shadow_plays-derived CASE-WHEN `side_won` formula V2 originally had — same bug shape, same risk. **Root cause of the spread/f5spread sign bug — confirmed via code tracing, not just real-settlement comparison (2026-07-22)**: `tonight/ml-spread.js` generates TWO candidate plays per physical spread ticker — one per team, whichever direction has the better MODEL EDGE wins an edge-dominance dedup and gets logged to `shadow_plays`. Separately, and independently, the maker engine's `computeMakerQuote` picks `quote_side` based on CURRENT market price at quote time (whichever side is priced as the favorite). These are two unrelated selections, made at different times, that can diverge. The old CASE-WHEN formula never checked whether `pick_team` (whichever team was captured) actually matches the ticker's own "margin team" (the team its yes/no is framed around, parseable from the ticker suffix, e.g. `"...-TB3"` → `"TB"`) — `direction` is null for spread rows, so nothing catches the mismatch. Confirmed concretely: a row with `pick_team="TOR"` graded against a `-TB3` ticker (margin team `"TB"`) produced the wrong sign. `shadow_plays` never stores which Kalshi side a row's `pick_team`/`won` corresponds to — that context only ever existed transiently in-memory during emission. **Scope confirmed narrow**: traced every consumer of `shadow_plays.won` for spread rows — taker-side ROI/calibration (`auth.js`), `category-gate.js`, `price-window.js`, and live pick-tracking (`liveStats.js`/`useLiveStats.js`) all compute win/loss strictly from a row's own captured fields with no later-introduced independent "side" to reconcile against, so none of them carry this bug. Only the maker engine (which introduces the independent `quote_side` re-selection) is affected.

**Fixed**: `computeSideWon()` (`maker.js`, exported) is now the single shared implementation — for `game_type='spread'`, it checks whether `pick_team` matches `marginTeamOf(ticker)` before deciding whether to flip `won`, instead of assuming they always match; every other game_type keeps the existing `direction`-based logic (safe there, since total/teamTotal's yes/no is ticker-invariant). Used by both `detectAndGradeMakerFills` (writes `maker_fills.side_won`/`pnl_cents`) and the `shadow-report` `makerBoard.quotedOutcomes` diagnostic (`handlers/shadow.js` — previously had its OWN hand-duplicated copy of the same buggy SQL CASE-WHEN, now computed in JS off raw rows so the two numbers can't drift apart again).

**Applied retroactively (was `POST /api/maker-v1-regrade`, ADMIN_KEY, since removed — see below)**: the grading step was split out of `detectAndGradeMakerFills` into its own exported `gradeMakerFills({ env })` (`maker.js`, kept — still called by `detectAndGradeMakerFills` and available for a future manual re-grade if needed) so it can be re-run against already-inserted `maker_fills` rows without re-replaying the trade tape. Confirmed working: `mlb|spread` went from +58.4¢/contract (CI-lo +43.1) to −8.3¢/contract (CI-lo −23.9) after the retroactive re-grade — total/teamTotal/ml rows recomputed to identical values as expected (their logic didn't change), only spread rows moved. **The precedence rule** (`api/lib/settlement-reconcile.js`): settlement is authoritative for the **14 shadow-only sports** in `SETTLEMENT_AUTHORITATIVE_SPORTS` (tennis, soccer, fight, golf, nascar, nbasl, lmb, mls, brasileirao, nwsl, chnsl, ligamx, scocup, argprem); the calibrated `teamRows` families (MLB/NBA/WNBA/NHL/NFL props, totals, ML, spread, segments) stay ESPN-graded and comparison-only. The split is principled, not merely cautious: **for ROI, settlement IS ground truth** (it's definitionally what a position was paid — the wrong Giants market really did pay the over), and ROI is the only thing the shadow-only rows measure (6 of the 14 are model-free, `truePct: null`, nothing to calibrate). **For model accuracy, physical reality is ground truth**, so anything feeding Brier/calibration keeps ESPN.

**ESPN deliberately keeps running on authoritative rows** rather than being skipped. Skipping them would be less code and would blind the only tripwire either feed has — that cross-check is what surfaced the mis-settlement. Instead, `reconcileGrades()` merges at **one chokepoint** immediately before `neonBatchResolve`, so **all 15 per-sport ESPN blocks were untouched** by Phase A — and, as designed, Phase B (2026-07-30) then deleted them wholesale without revisiting the merge (see below). Output is deduped by id, so it's safe to hand straight to `neonBatchResolve`.

Precedence details:
- **Settlement graded + ESPN graded, same answer** → `agreedWithEspn++`, grade written unchanged.
- **Settlement graded + ESPN graded, different** → `disagreed++`, sampled and logged, **settlement wins**.
- **Settlement graded + ESPN abandoned (`won:null`) or never reached** → settlement grade written, counted as `espnCouldNotGrade` (split into `espnNulled`/`espnAbsent`). This is the biggest practical win — rows the ESPN path could never resolve now resolve.
- **Void (`result:"scalar"`)** → `won=NULL`, resolved immediately (the abandon idiom) instead of waiting out the 14-day sweep. **This overrides even a real ESPN grade**, deliberately: a voided market contributes nothing to ROI, so keeping a win/loss on it would corrupt the only number these rows produce, and an ESPN grade on a Kalshi-voided market usually means ESPN matched the wrong event (a rescheduled game, or tennis's whole-tournament scoreboard). Counted as `voidedOverridingEspn` so a spike is visible rather than silent.
- **Everything else** → passes through exactly as ESPN graded it. The function is a strict no-op for the calibrated families.

`classifyTickerSide`/`classifyRowViaKalshi` (new, three-state `pending`/`void`/`graded`) exist because the older null-returning helpers collapse pending and void into one `null` — correct for maker PnL (both mean "don't book yet"), wrong here, where void is terminal. The old helpers became thin wrappers with **identical contracts**, so `maker.js` and `maker-live.js` needed no changes (pinned by a test asserting a real loss still returns `false`, not `null`, through the `??` in the wrapper).

**Observability**: `kalshiGrading: {graded, voided, voidedOverridingEspn, agreedWithEspn, disagreed, espnCouldNotGrade, bySport, disagreements}` on the response plus a per-sport log line. `noData` is still an ESPN-feed metric that counts rows settlement went on to resolve, so **`noDataNetOfSettlement`** (= `noData − espnAbsent`) is the real "still unresolved" number — read that one, not `noData`, when judging a run.

**Circularity guard on `/api/kalshi-dryrun-check`**: that endpoint compares each row's stored `won` against settlement, so once settlement writes `won` for the 14 sports, those rows agree *by construction*. Rows of an authoritative sport resolved on/after `SETTLEMENT_CUTOVER_DATE` (2026-07-25) are excluded from `agree`/`disagree` and reported under `circular: {excluded, bySport, cutoverDate, authoritativeSports}`; pre-cutover rows of the same sports still carry genuine ESPN grades and remain a real comparison. Without this the endpoint would have quietly started reporting an inflated agreement rate.

Failure-closed: a settlement-fetch throw empties both maps and every row falls through to the ESPN path precisely as before.

**The tripwire was flaky until 2026-07-26 — silent chunk drops.** `fetchKalshiSettlements` batches tickers 200 at a time and, on any non-ok or throw, dropped the whole chunk with `if (!res.ok) continue` + a bare `catch {}` and no counter. Found while checking in on Phase A's first live cron: four back-to-back `/api/kalshi-dryrun-check` runs over an *identical* 5510-row input returned `settlementsFound` of 2200 / 2000 / 2600 / 2600 — exact multiples of 200, i.e. whole chunks vanishing at random — with `comparedAgainstEspn` 2867 / 2952 / 3478 / 3478 and `disagree` **0** / 2 / 2 / 2. The `disagree: 0` run looked like a perfect 100% score but was simply the run that never fetched the chunk containing `KXMLBTEAMTOTAL-26JUL242215LAASF-SF8`, the one known bad settlement. *A tripwire that reports "all clear" because it failed to look is worse than no tripwire* — and Phase A's whole safety argument rests on `disagreed` staying live.

Grading was never wrong: a ticker missing from the map classifies as `pending`, so those rows just retry next cron (failure-closed held). The damage was purely observational — the resolver under-graded invisibly and `kalshiGrading.graded` under-reported with no signal.

Fix (`fetchKalshiSettlementsWithMeta`): 3 attempts per chunk with 250ms/750ms backoff, a **fresh `AbortSignal` per attempt** (a retry gets a full 10s budget, not the remains of the first one), and failure telemetry travelling with the data — `{settlements, meta:{tickersRequested, tickersFound, chunksTotal, chunksFailed, chunksRetried, failures[≤5]}}` plus a `console.warn` on any failure. `fetchKalshiSettlements` remains a Map-returning wrapper so `maker.js` V1 grading and shadow-report's `quotedOutcomes` are untouched. Both `/api/kalshi-dryrun-check` and the resolver's `kalshiGrading` now carry `settlementFetch` + `incomplete`; **read `incomplete` before any agreement number** — a `true` there means the denominators are a floor and `disagree: 0` proves nothing.

**Codebase-wide 414 audit (2026-07-26) — `fetchKalshiSettlements` was the only affected site; don't re-audit.** Swept every place a list is joined into a URL. `kalshi-flow.js` and `kalshi-series-check.js` (the two flagged as same-shape suspects) turn out **not** to batch at all — one ticker per request (`?ticker=`, `?series_ticker=`), so there is no list to overflow. The four genuine batch-into-URL sites all have real headroom against the ~8KB ceiling: `mlb-pitchers.js` ~60 six-digit personIds ≈ 530-char URL (~15×); `mlb-hitters.js` ~300 personIds ≈ 2,300 chars (~3.5× — **the tightest, worth re-checking if it ever grows**, though it's structurally bounded: `teamLineups` is keyed by team abbr, so extra schedule dates overwrite rather than accumulate, capping it at 30 teams × ~10); `mlb-weather.js` ~15 lat/lon pairs ≈ 130 chars per param (~60×); and `shadow.js`'s four `fetchLiveInto` calls → `/api/live?games=` at ~50 game keys × ~44 encoded chars ≈ 2,200 against Vercel's larger ~14KB request limit (~6×, and scoped to `teamRows` — mlb/nba/wnba/nhl/nfl only). Note `game_time` is a **TEXT** column, so keys embed a ~20-char ISO string, not a 60-char `Date.toString()` — worth remembering, since the latter would roughly triple encoded key length. The remaining `join(",")` hits (`sportsbook.js`'s cache key, `market_types`/`tags` column values) never enter a URL. A 414 on `fetchLiveInto` would also be *loud* rather than silent — it logs the status, retries once, then the date's rows land in `noData` — unlike the settlement path, which is exactly why that one hid for so long.

**Cause: HTTP 414, named by the telemetry itself on its first live run.** The initial deploy came back `incomplete: true, chunksFailed: 1/18, chunksRetried: 9, failures: [{chunkIndex: 14, size: 200, reason: "HTTP 414"}]` — URI Too Long, not the timeout/gate interaction that was the leading suspect beforehand. A 200-ticker chunk is ~7.5KB of query string at ~37 chars/ticker, so any chunk holding longer-than-average tickers crossed the ~8KB URL ceiling. Deterministic per chunk, but *which* tickers land in chunk N shifts as the row set grows — hence the random-looking flakiness. Second-pass fix: `chunkTickers()` bounds each request by **encoded query length (`MAX_TICKER_QUERY_CHARS` 6000) as well as count**, and `isRetryableStatus()` fails fast on deterministic 4xx (414) while still retrying 429/5xx. The retries stay useful regardless — `chunksRetried: 9` on that same run means genuinely transient failures were being recovered on attempt 2. Worth noting as a method point: the observability was added *before* the cause was known, and then produced the cause on first contact.

Matches prices to today's `shadow_plays` by `shadowId` (only rows with `price_pre_at IS NULL`), batch-upserts `kalshi_yes_price_pre`/`kalshi_no_price_pre`/`price_pre_at`. The unstamped-rows SELECT goes through the pooled primary (`{write:true}` — read-after-write of rows the snapshot cron inserted earlier today; the 03:00 UTC run is the coldest Neon touch of the day) and logs `unstamped rows=N` — a Neon failure is logged, not silently swallowed into `updated:0`. **The 2-pass→5-pass widening (2026-06-29)** hardens against the two intermittent-dip modes: (A) a degraded morning staging priceMap (`priceMapSize ≪ unstampedRows` → the 12:30pm pass recovers it before day games settle out of staging — 6/28 captured 63 vs the ~1000 a healthy first pass gets) and (B) late-listed categories (soccer/WNBA) missing the fixed run times (6/26 soccer 39%). **Per-run breadcrumb:** every real run appends `{ranAt, source, stagingAgeMs, priceMapSize, unstampedRows, captured}` to KV `shadow:pregame:{date}` (30h TTL, last 12); read via `GET ?runs=1[&date=]` to root-cause a dip without log archaeology (degraded staging shows `priceMapSize ≪ unstampedRows`; a late-listing shows low `captured` with a full priceMap). `?dry=1` runs everything except the DB write and returns `{source, stagingAgeMs, priceMapSize, unstampedRows, wouldUpdate, skipped}` — use it to verify without stamping mid-game prices as "pregame". CLV = bet-side `price_pre - price_snap`; positive = market confirmed the model direction. **CLV-capture health is measured over the `snapshot_date` cohort** (shadow-report `dataHealth.clvCapture`, see CLAUDE.md); steady-state ~95%/day, multi-day rate via `GET /api/auth/shadow-analysis?clvCaptureHistory=1` and per-day forensics via `?clvDay=YYYY-MM-DD` (per-run hour buckets + per-sport capture).

## Data Plumbing Gotchas

**Global fetch concurrency gate (`api/lib/fetch-limit.js`, 2026-07-05)**: the function instance has a **1024 file-descriptor ceiling**, and total open sockets ≈ the **sum of every module's peak `Promise.all` burst width** — undici opens one socket per concurrent request and keeps finished sockets pooled for keep-alive past the whole request (idle pooled sockets are unref'd, so `getActiveResourcesInfo` doesn't show them; only `/proc/self/fd` does). Crossing the ceiling makes EVERY subsequent outbound fetch in the run fail — ESPN and Upstash alike — as `TypeError: fetch failed` with `e.cause.code` `EMFILE`/`EBUSY`, while single-fetch routes and the snapshot cron stay healthy (that asymmetry is the diagnostic). The guarantee is `fetch-limit.js`: a 64-slot `pLimit` gate wrapping `globalThis.fetch`, side-effect-imported as the FIRST line of `api/[...path].js` so every caller (ESPN, statsapi, Kalshi, Upstash `cmd`, Neon driver) shares the budget — with ≤64 in flight, undici reuses pooled sockets instead of opening one per burst member (measured: byteam-phase fds 1024 → 168). On top of the gate, keep the pacing idioms: wide fetch loops through `pLimit(n)` (`api/lib/utils.js`, n≈16–20 — tonight player hydration, mlb-pitchers gamelogs/PBP) and per-key KV reads over lists via `cache.getMany(keys, type)` (chunked MGET in `makeCache`, 20 keys/chunk; feature-test `CACHE2.getMany`, fall back to parallel GETs). Don't introduce a fetch path that bypasses global `fetch`. Diagnose with `/api/tonight?debug=1` → `fdProbe` phase milestones (start/afterKalshi/afterByteam/…, per-fd readlink classification). Trigger history: the 7/03 capture-band widening (+~25% qualifying markets → more players/markets per run) pushed cumulative burst width over the ceiling; symptom was the dashboard's "No games scheduled" (all `gameTime:null`, 96% of gamelogs failing, ~10 plays instead of ~600).

**gameTimes lookup chain** (in play loop): `sport:team:gameDate` → `sport:team:tomorrowISOStr` → bare `sport:team`.

**gameTimes built from a DEDICATED scoreboard fetch, with a gameScores backfill (2026-06-13)**: The `gameTimes` map comes from its own ESPN scoreboard fetch (`tonight.js` ~678), SEPARATE from the per-sport `gameScores` maps (MLB via `buildMlbByteam`, others via their byteam builders). When that one fetch silently 429s/times out (`.then(r => r.ok ? r.json() : {})` swallows it), `gameTimes` comes back empty → every play gets `gameTime:null` → duplicate matchup cards client-side + the started-game pre-game drop (~1417) no-ops. Self-heals next request (cache not written when empty — the `Object.keys().length > 0` guard at ~705). A per-request backfill loop just before `emitPropPlays` (~1374) fills any **absent** `gameTimes` keys from the independently-fetched `gameScores` (preserves the dedicated fetch's DH "latest UTC time wins" entries; not written back to cache). Diagnose a recurrence: `curl .../api/tonight | jq '[.plays[]|.gameTime]|unique'` — all-null means BOTH the dedicated fetch and gameScores were empty (full ESPN outage), not just the dedicated one.

**`_mlbMlContext` null-gameDate fallback (2026-05-29)**: KXMLBTOTAL tickers routinely have unparseable date segments. Context stored as `_mlbMlContext["HOME|AWAY|null"]`. All context lookups chain `?? _mlbMlContext["t1|t2|null"] ?? _mlbMlContext["t2|t1|null"]` fallback. Symptom if broken: F5/spread/ML plays absent; totalRuns plays present with `gameDate: null`.

**Kalshi MLB postponed-ticker reattribution**: When a game is rained out Kalshi reuses the original ticker. After `sportByteam.mlb` hydrates, `_mlbNextGameByTeams` is built from `state === 'pre'` gameScores entries; `_reattrMlbGameDate` overwrites stale dates on market arrays. Resolved markets (extreme prices) are skipped to prevent yesterday's settled prices from being misattributed.

**Closing-line snapshots** (`mlbClosingOdds` / `nbaClosingOdds` / etc.): ESPN returns empty `odds` once a game is in/post. Redis key per sport holds the last-seen pre-game line. `state==='pre'` writes; `state==='in'|'post'` overlays back. 36h TTL. If no snapshot exists for an in/post game, odds entries are **cleared** rather than shown (model-derived mid-game prices look like real lines but mislead).

**`mlbMeta.gameOdds` vs `mlbMetaTomorrow.gameOdds`**: Today's odds from `parseGameOdds(sbData.events)`; tomorrow's from `parseGameOdds(sbData.eventsTomorrow)`. Both normalized through `MLB_ESPN_NORM`. `MatchupCard` selects by `game.gameDate` vs PT today.

**Kalshi-derived MLB odds fallback**: ESPN doesn't post tomorrow's lines until close to first pitch. Already-fetched `KXMLBGAME`/`KXMLBTOTAL` arrays fill missing fields on `_mlbGameOdds`/`_mlbGameOddsTomorrow` only — ESPN stays authoritative when present.

**`{sport}Meta.topPlayers[abbr]`**: `{ name, id, headshot, stats }` from ESPN scoreboard `competitions[].competitors[].leaders` by `parseTopPlayers` in `api/lib/utils.js`. NBA/WNBA: `RAT` leader; NHL: `Points` leader (derives G or A from secondary leaders when present).

**byteam:mlb partial-cache trap**: MLB byteam hydrates several API calls in parallel and each `.catch(() => ({}))` silently. Short-TTL guard (60s) fires when any of `lineupSpotByName`, `pitcherAvgPitches`, `hitterOpsMap`, `pitcherH2HStarts` is empty. Symptom: ReportPage Market tab columns null; diff cached vs `?bust=1` to confirm.

**Two-way players** (MLB strikeouts): ESPN gamelog defaults to batting stats. The play loop appends `&category=pitching` for K-market players. Separate cache keys (`gl:mlb242526pv1`, `gl:mlb2025p|`, `gl:mlb2026p|`) prevent batting/pitching collision. Without this, two-way players drop with `col_not_found`.

**ESPN gamelog endpoint**: ESPN blocks server-side HTML fetches with AWS WAF. Use the JSON API (`site.web.api.espn.com/apis/common/v3/sports/{sport}/{league}/athletes/{id}/gamelog`) for ALL sports.

**NBA lineup source chain**: (1) ESPN scoreboard → game summary boxscore starters (`lineupConfirmed:true`); (2) most recent **playoff** game first (`seasontype=3`), fallback to last regular-season `lastGameId`; (3) ESPN team roster. ESPN depth chart returns `{}` during playoffs — removed. Prefer playoff over RS — RS finals can have rested/bench starters.

**MLB lineup** (`/api/team`): (1) MLB Stats API `hydrate=lineups,probables` today → `lineupConfirmed:true`; (2) most-recent posted lineup from past-10-day schedule → `lineupConfirmed:false`; (3) active roster fallback. Probable-pitcher entry is preserved across (2).

**`mlbMeta.pitchers[abbr]` shape**: `{ name, id, era, wins, losses }`. `pitcherEra` is the two-step-regressed value (same as the lambda math uses), not raw season ERA. Sources merged in `api/[...path].js` ~line 4890: name/id/era from pitcherInfoByTeam → probables fallback.

**NHL_ABBR_MAP**: NHL Stats API teamIds → abbreviations. **UTA (Utah Mammoth) = teamId 68** (rebranded 2025-26; old teamId 53 absent). New teams showing `—` need their teamId added.
