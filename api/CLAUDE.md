# api/ — module map

Loads when working under `api/`. Root `CLAUDE.md` holds the always-on doctrine (qualification, capture window, category gate, Key Gotchas); this file is the per-module map. Route contracts live in the `api-routes` skill.

### API: `api/[...path].js` (router) + `api/lib/handlers/*.js` (routes) + `api/lib/*.js` (modules)

`api/[...path].js` is a thin router: CORS preflight, `makeCache`, dispatch to one handler per route family.

Absent (key expired past 48h, run predates the ship, or a cache with no `hgetall`) → the old generic wording, which is the honest answer then. Failure-closed inside the existing `dataFreshness` try/catch. `discovery` is the series-scan vet queue (`venue:"kalshi"` — every row is a Kalshi `KX*` series; `counts` by status, `toVet` = `status IN (new,shortlisted) AND screen='REAL_BOOK'` with a `perGame` flag that marks bare-prefix futures vs GAME-suffix per-game markets, `autoDismissedToday`) — the scan cron runs 15 min before the report cron, so it's same-morning fresh. **Framed as candidates to VET, never build**: `screen=REAL_BOOK` proves a real book, not buildability (GAME-suffix, ESPN slug, team-abbr cross-check are human vetting — see the KXUCLGAME deferral). **`discovery.polymarket` added 2026-08-05** — a sibling lane from `polymarket_sports_seen` (`counts` by status + `toVet` leagues with `marketTypes`/`sampleEvent`/`liveEvents`), **its OWN nested try/catch** so a missing poly table can't blank the Kalshi list. It is per-LEAGUE (Gamma sport slug), NOT per-market-family, so it is NOT joined to the Kalshi candidates per-row — Gamma slugs (`argcopa`, `bel1`) share no key with Kalshi tickers, and active cross-venue *capture* is mlb/nba/nhl/wnba only. Read it as the cross-venue availability answer at league grain: a Kalshi candidate whose league also appears here with the matching family extends `venueVig` coverage. **`uiHealth` added 2026-08-02** — top-level report field asserting the LANDING PAGE's rendered payload is present + complete. `dataFreshness` answers "is the data current?"; `uiHealth` answers "will the page render?" — orthogonal, because an on-time report can still ship an empty/degenerate `categoryBands` (blank board) or a cell missing a render field (blank/NaN square). Pure `computeUiHealth(makerBoard, preregistrations)` over the in-memory payload (no Neon), so it can never disagree with what ships; validates BOTH things `MakerBoardPage` draws — `CategoryBandHeatmap`(`makerBoard.categoryBands[].{sport,category,band,contracts,perContract}` = render-critical; `reliable`/`anomaly`/`fills`/… are tooltip/style-only, counted not gated) and `PreregTracker`(`preregistrations[].{id,verdict,checkpoint,forwardStart,label,checks[]}`). Shape `{ok, heatmap:{rendered,cells,rows,rowsShown,rowsHidden,reliableCells,anomalyCells,cellsMissingRenderField}, preregTracker:{rendered,cards,malformed}, warnings[]}`. `_HEATMAP_MAX_ROWS` mirrors the component default (advisory, drift is cosmetic). **`robustCandidates` added 2026-08-03** — top-level morning-report field (NOT read by the frontend), the heatmap-robustness TRIPWIRE. The category×band grid is a map of noise (555 cells, ~1/40 clear a 95% CI by chance), so eyeballing the greenest and "advancing" it is the in-sample target-picker the REENTRY doctrine has gone 0-for-6 on. `computeRobustCandidates(makerBoard)` (pure, exported + tested) is the disciplined inverse: a cell must cross a strict STRUCTURAL bar before it is even a pre-registration candidate — `reliable` (day-clustered CI already excludes zero, positive side; a robust NEGATIVE cell is an anomaly/integrity concern, excluded here by construction) AND the f5total pre-registration's own sample floor: `ROBUST_BAR` `{minDays:8, minFills:50, maxTopDayShare:0.35}`. A hit is a prompt to design a mechanism-first `docs/MAKER_*_PREREG.md`, NEVER a bet or a ranked shortlist — robustness is necessary, not sufficient (f5total was clean in-sample and inverted forward). **"Expected output is NONE" was CORRECTED 2026-08-11**: it was true at ship because n was small, not because a hit implies edge. The day-clustered CI narrows as days accumulate, so any cell with a nonzero *structural* offset eventually crosses `ciLo > 0` — on a price-monotone book that is most of the board, and `count` therefore measures sample size. The 8/11 read was **23 positive / 26 NEGATIVE of 210 eligible** against a ~10.5-per-arm noise floor, with 22/23 positives below 50¢ and 26/26 negatives at 50¢+ — the band-ladder artifact (`docs/MAKER_LADDER_ARTIFACT.md`), i.e. the tripwire was reporting one arm of a near-symmetric distribution. So the payload now carries the denominator and both arms: Shape `{bar, eligible, noiseFloor, count, negativeCount, candidates:[{cell,sport,category,band,fills,days,perContract,ciLo,ciHi,topDayShare}], negatives:[…same…], note}`. **The signal is the ASYMMETRY between the arms, never `count` alone.** `candidates`/`negatives` are sorted by cell NAME, not `perContract` — a perContract-descending array is a ranked shortlist whatever the note says (same objection that killed the "best-green" heatmap shade). The `note` travels with the payload so the morning report can't restate it as "top picks". Bar, `ROBUST_ONE_SIDED_RATE`, both arms, and the ordering pinned in `report.test.js`. Still missing (deliberately, needs its own design pass): an anomaly filter — `computeRobustCandidates` has none, though `docs/MAKER_TOTALRUNS_PREREG.md` criterion 6 claims one, and `wnba|totalPoints|15-19` is anomaly-flagged, in `candidates`, and live prereg `wnbatp-1519`. The anomaly detector's null is "price = realized frequency", which the ladder violates by construction, so it currently flags ladder endpoints rather than wrong-side-fill bugs. **Anomaly flag REWRITTEN 2026-08-11** (`ladderAnomalies` in `api/lib/maker-stats.js`, pure+tested). The old inline test asked whether a cell's outcome was pinned against its own PRICE (`tail = (1-p)^fills < 0.001` at the band midpoint) — the exact null the band-ladder artifact falsifies (`docs/MAKER_LADDER_ARTIFACT.md`), since every book's realized sideWon is a monotone function of price sitting well off the diagonal. It therefore fired on the ENDS of steep ladders and nowhere else: **all 6 flagged cells on 8/11 sat within 0.07 of their own ladder while sitting 0.12-0.28 from their price.** Worse, it only evaluated cells with `sideWon` EXACTLY 0 or 1 — but a wrong-side fill does not pin an outcome, it INVERTS one (a 15-19¢ cell grading ~0.85 where ~0.07 belongs), so **the detector could not see the bug it was named for.** New null = the category's own monotone price→outcome curve: weighted isotonic (PAVA) fit over band midpoints, **leave-one-out**, read by distance-weighted interpolation between the neighbouring rungs (NOT a plain average — bands are unevenly spaced and categories skip rungs). Flag when the residual is significant against the **combined** day-clustered SE of cell AND reference (treating the fitted reference as exact was the first draft's error — it flagged ordinary mid-ladder roughness, 27 cells) AND `|residual| >= LADDER_BAR.minResidual` 0.15. A **category-level** check runs first: a wholesale side-flip in one emit module inverts every band together, leaving each cell near a flattened fit and invisible per-cell, so a ladder whose sideWon FALLS as price rises flags the whole category. `LADDER_BAR {minFills:20, minDays:3, minTickers:5, minBands:4, minResidual:0.15, maxSpanC:10}` (pinned in `maker-stats.test.js`); failure-closed — a ladder too sparse to calibrate flags nothing rather than falling back to the price null. **`maxSpanC`/`minTickers` added hours later**, after the first version's loudest cluster (`mlb|f5spread` 40-64) was investigated and proved to be the DETECTOR's thinness, not a pipeline fault: grading verified 3/3 against Kalshi settlement, and the new read-only `?makerBookAudit=sport|category` showed the books exactly complementary and tight (`avgNoSpread`==`avgYesSpread` to 2dp, ask-sum 101.1-101.7, **0 of 2489 fills** with a wide NO book behind a tight YES one). `maxSpanC` refuses a reference interpolated across >10c of unobserved ladder (55-59's rungs were 20c apart once 45-49 n=5 and 50-54 n=16 were dropped); `minTickers` counts distinct GAMES via a `COUNT(DISTINCT ticker)` roll-up (not derivable from the per-day grain — summing per-day distinct counts double-counts a ticker quoted on two days). Counting non-degenerate DAYS instead was rejected on the data: ladder ends are legitimately degenerate (85-89 is 10/21), so it would silence the extreme cells the rewrite exists to watch. **Measured: 13 flags -> 9, ALL four cleared by `maxSpanC`; `minTickers` cleared nothing and does not measure the thinness it was added for** — 55-59 touches 25 distinct games while still having 14 of 17 days at one game, i.e. fills concentrate per-day without the cell's total game count being small.
