# api/ — module map

Loads when working under `api/`. Root `CLAUDE.md` holds the always-on doctrine (qualification, capture window, category gate, Key Gotchas); this file is the per-module map. Route contracts live in the `api-routes` skill.

### API: `api/[...path].js` (router) + `api/lib/handlers/*.js` (routes) + `api/lib/*.js` (modules)

`api/[...path].js` is a thin router: CORS preflight, `makeCache`, dispatch to one handler per route family.

- `maker-stats.js` — **contract-weighted maker PnL + CI** (2026-07-25). `contractWeightedPnl()` (pure, from six plain sums) + `weightedPnlSumsSql`/`weightedPnlFromRow`; surfaces as `makerBoard.fills.weighted` and `makerBoard.live.weighted`. Exists because both boards' headline `avgPnlCents` is an UNWEIGHTED per-FILL mean — a 1-contract and a 500-contract fill count equally, but capital earns the weighted number. **The trap it avoids**: weighting by treating each CONTRACT as an observation is wrong, because all contracts in one fill share a single outcome (perfectly correlated) — that inflates effective n by mean fill size (~6.6× on V1's book) and shrinks the CI ~2.6×, enough to arm real money on noise. The fill is the independent unit, so the weighted mean is a **ratio estimator** with a delta-method variance (`Var(R) ≈ (n/(n−1))·Σ[cᵢ(pᵢ−R)]²/(Σcᵢ)²`), pinned by a test proving it collapses to the textbook `s²/n` when all weights are 1. **`dayClusteredPnl()` (2026-07-26) — the interval to actually act on**, surfaced as `makerBoard.{fills,live}.dayClustered`. Same ratio estimator with the **DAY as the cluster**: `weighted` fixed correlation WITHIN a fill, this fixes correlation ACROSS fills sharing a day (V1 sells favorites, so a day's PnL is one bet on whether favorites underperformed that slate — hundreds of fills resolve off a few dozen correlated games). Not a small correction: on 2026-07-26 the same data gave `weighted` [+0.70, +2.81] (criterion satisfied) vs `dayClustered` **[−3.00, +6.47]** — point estimate unmoved (+1.76 → +1.73), interval ~4.5× wider and crossing zero, because +$1,865 of the +$1,066 total came from **two** of seven days. `armCriterion` now carries `need` (historical `pnlLoCI > 0`), `needClustered` (`dayClustered.loCI > 0`), `minDays` 14, and a computed `met` combining all three — read `met`, never `need` alone.

Both old helpers are now thin wrappers, contract unchanged (`maker.js`/`maker-live.js` untouched). **`fetchKalshiSettlementsWithMeta` (2026-07-26) — the batch fetch now retries and REPORTS its own failures.** It previously dropped a whole 200-ticker chunk on any non-ok/throw with zero trace (`if (!res.ok) continue` + bare `catch {}`); four back-to-back `/api/kalshi-dryrun-check` runs over an identical 5510-row input returned `settlementsFound` of 2200/2000/2600/2600, and the 2200 run reported a clean `disagree: 0` **only because the chunk holding the one known bad settlement was never fetched** — a tripwire reporting "all clear" when it simply failed to look. Grading itself was never wrong (a missing ticker classifies `pending` and retries next pass), but the resolver under-graded invisibly. **Cause was HTTP 414 (URI Too Long)** — named by this telemetry on its own first live run, not by the pre-deploy hypothesis: 200 tickers ≈ 7.5KB of query string vs the ~8KB URL ceiling, so chunks holding longer tickers 414'd; which tickers land in chunk N shifts as the row set grows, hence the random-looking flakiness. `chunkTickers()` now bounds each request by **encoded query length (`MAX_TICKER_QUERY_CHARS` 6000) as well as count**, and `isRetryableStatus()` fails fast on deterministic 4xx while retrying 429/5xx; 3 attempts/chunk with backoff + a fresh `AbortSignal` per attempt stay for the genuinely transient failures (9 retries recovered on that same run). Returns `{settlements, meta:{tickersRequested,tickersFound,chunksTotal,chunksFailed,chunksRetried,failures}}`; `fetchKalshiSettlements` stays a Map-returning wrapper for `maker.js` + shadow-report's `quotedOutcomes`. **Read `chunksFailed`/`incomplete` before trusting any agreement number** — surfaced on both `/api/kalshi-dryrun-check` and the resolver's `kalshiGrading`.
